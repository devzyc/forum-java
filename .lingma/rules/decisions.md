# 架构决策记录

## 标签系统：合并进发文流程

- 结论：废除独立接口 `POST /tag/create`，新标签在发布文章时自动创建并绑定。
- 理由：独立创建接口允许用户制造大量不挂任何文章的空洞标签；合并方案保证每个新标签诞生时至少关联当前这篇文章，从源头杜绝空标签。代价是发文接口逻辑变复杂，但换取数据纯净。
- 配套限制：单篇最多 20 个标签，防止批量滥用。
- 被否决方案：
  - 保留创建接口并用定时任务清理空标签。否决原因：只是隐藏问题而非根治，还要额外开发和运维成本。
  - 给创建接口加前置验证。否决原因：无法解决"创建后不发帖"的核心场景。
- 适用边界：当前用于 UGC 社区内容管理；若将来需要纯标签库或词典能力，需重新评估。

## 去除 `-rest` 路径后缀

- 结论：新接口不再带 `-rest` 后缀；存量 `/article-rest`、`/user-rest` 前缀保持不动，避免影响小程序端已发布版本。
- 理由：属于无信息量的冗余命名，去掉后路径更直白，符合"做一件事并做好"的取向。
- 被否决方案：一次性重命名存量接口。否决原因：会让已上线的小程序端全部失效，收益不足。

## 后端瘦身形态

- 结论：后端收缩为纯 REST 服务，只服务小程序端。
- 已移除：Thymeleaf 服务端页面、GitHub OAuth 登录、FAQ 模块、后台管理入口。
- 影响：任何涉及页面渲染、OAuth 登录流程、后台管理的需求都不再在当前仓库范围内，先确认需求是否还有效。

## 发文数据模型收敛

- 结论：发文不再区分 `typeId` 与 `ContentType`，正文只保留 `html_content`。
- 影响：写接口或查询时不要再引入类型字段；历史 Markdown 兼容逻辑应删除而非保留。
- [待确认] 旧数据中 `typeId` 的过渡取值是否还有后端校验，需要按实际代码确认。

## 缓存演进

- 当前：`DbCacheServiceImpl` 是单机内存 Map 加定时刷库，适用于单实例部署。
- 演进条件：多实例部署时必须换成 Redis。
- 改造方式：domain 层接口保持不变，只新增实现类并切换装配，调用方代码不改。
- 判定信号：出现"登录后另一台机器查不到会话"这类现象，就是该换 Redis 了。
