# 通用工程原则

## 简洁性优先

- 设计方案时先问一句：这份复杂度是否必要。若无安全、隔离之类的硬理由，选最直接的形式。
- 判定信号：参数过多、名称冗长、划分过细、为了"将来可能"而预留的抽象，都属于可消除的复杂度。
- 典型反例：按邮箱区分 token 文件名（实际只需一个固定名）；接口路径挂 `-rest` 冗余后缀。
- 符合的原则是「做一件事，并做好」，不是「每个场景都单独铺一套」。

## 编码风格：对齐现状，不加额外规范

- 本项目不设独立的代码格式规范。写代码前先看同目录、同类角色的既有代码，照其命名、缩进、异常处理、日志写法来写。
- 功能实现优先于风格洁癖。类型、注释、命名跟着周边代码走，不要单点引入新风格。
- 改动范围只覆盖需求本身，不顺手规范化无关代码。

## 重构边界

- 抽取公共代码的前提是有两个以上真实调用方；只有一个调用方时直接内联，不做预判式抽象。
- 需求变化导致原有抽象的理由消失时（例如共享校验文件被删、常量只剩一处引用），应一并内联或删除，不能因为"曾经有用"而保留。
- 常量保留的判断标准是跨语句一致性需求，而不是引用次数。两处必须强一致（如 toast 时长与定时器延时）才值得抽成常量。

## 结论表达

- 说明技术决策时按四段写：结论、取舍理由、被否决的备选方案及否决原因、适用范围或失效条件。
- 只写"做了什么"没有价值，要写清"为什么这样选"以及"什么时候需要重新评估"。
